# 稳定性与上下文管理

> 0.4.1 起的可靠性机制：为什么"重启后继续长对话必超时"、代理如何裁剪上下文、
> 看门狗与熔断的参数，以及"输出一顿一顿"的原因。

## 背景：大 prompt 的确定性超时

2026-11-17 实测（真实会话折叠重放 + 体积二分）：

| 折叠后 prompt | 结果 |
|---|---|
| 20,000 字符 | ✅ 2.5 秒完成 |
| 35,000 字符 | ✅ 秒级完成 |
| 50,000 字符 | ⚠️ 静默 75–90 秒后完成 |
| 80,000 / 150,000 / 336,000 字符 | ❌ >120 秒无内容，被看门狗/客户端掐断 |

机制：prompt 越大，模型"思考"（reasoning）产出越多，而**上游网关要等思考结束才开始吐内容**。
内核日志佐证：20k 字符输入 → 输出 777 tokens；50k → 输出 7,774 tokens。

由此形成的故障链：桌面端或代理重启后，长对话的第一轮要把整段历史折叠重放 →
巨大 prompt → 长静默 → 超时；客户端重试时每次重放同样的内容 → **确定性失败**，
只能反复手动发"请继续"。0.4.1 起在四个层面处理这个问题；0.4.2 增加第五层
（长对话历史存档与按需检索，见专节）——因为实测发现单靠体积裁剪仍挡不住
`chat-pro × 超大对话消息` 的静默卡死。

## 五层上下文控制

| 层 | 环境变量 | 默认 | 行为 |
|---|---|---|---|
| **长对话历史存档** | `TA_ARCHIVE_MIN_CHARS` / `TA_RECENT_CHARS` | `12000` / `10000` | **首轮**（如重启/切模型后）若历史超过阈值，完整历史落盘到 `runtime/archive/<会话指纹>.md`，只把最近约 `TA_RECENT_CHARS` 字符 + 一段"完整历史已存档、动手前先检索"的指针发给模型。见下方专节 |
| 单轮总体积 | `TA_MAX_FOLD_CHARS` | `40000` | 首轮折叠与增量轮共用同一预算：超限时**优先丢弃最旧的工具结果**（用户/助手主线保真），文本头注明省略；工具结果丢完仍超限才截尾保留最近内容。`0`=关闭 |
| 单条工具结果 | `TA_MAX_TOOL_CHARS` | `12000` | 超长工具结果保留 60% 头 + 40% 尾，中间标"省略 N 字符"。`0`=关闭 |
| 流空闲看门狗 | `TA_STREAM_IDLE_MS` | `240000` | 该时间内**内容没有任何增长**才判定上游静默断流（错误码 `UPSTREAM_IDLE`）。思维链增长、正文增长、新的 assistant 消息都算活跃；重复回吐同一段文本骗不过它。`0`=关闭 |
| 单轮总时长 | `TA_TURN_TIMEOUT_MS` | `1200000` | 一轮 20 分钟硬上限 |

设计原则：

- **丢最旧的工具结果，不丢对话主线**——用户意图与模型已得出的结论完整保留；
  被裁掉的早期工具输出在需要时模型会重新调用工具获取，代价是多一轮往返
- 模型始终被告知有省略（折叠文本头部标记），不会把裁剪后的内容当成完整历史
- 三协议（`/v1/chat/completions`、`/v1/responses`、`/v1/messages`）的折叠与裁剪行为一致

裁剪发生时代理日志会出现（时间戳格式，可与内核日志毫秒级对表）：

```
[2026/11/17 08:23:40.123] 首轮折叠文本裁剪：省略 8 条工具结果，剩余 20073 字符
[2026/11/17 08:23:40.456] 增量轮裁剪：省略 2 条、截取 1 条工具结果，本轮 39812 字符
```

## 看门狗为什么是 240 秒

实测"活着但静默思考"的窗口随 prompt 变大：50k 字符静默 75–90 秒属正常；
真实会话 35k 重放中观测到 **163.9 秒完全静默后一次性返回 66,500 字思维链**。
120 秒（0.4.0 默认）会把这类本来能完成的轮次误杀；240 秒给足长思考耐心，
又略短于 DSH 客户端自身的 300 秒流空闲超时——真卡死时，可定位的
`UPSTREAM_IDLE` 错误会先从代理报出，而不是客户端笼统超时。

## 长对话历史存档与按需检索（0.4.2）

### 为什么选择这样做

0.4.1 的体积裁剪（40k 上限）对**工具结果**有效，但对**对话消息本身**很大的会话仍会卡死。
2026-11-17 用真实会话逐项排除后定位到唯一组合：`chat-pro` + 超大对话消息。

| 对照实验 | 模型 | 输入 | 结果 |
|---|---|---|---|
| 全新对话问"晚上吃什么" | chat-flash | 对话消息仅 0.9%（~3.6k） | ✅ 22 秒 |
| 全新对话"推荐几个菜" | chat-pro | 38.7k 固定开销，对话消息 0.9% | ✅ 6 秒 / 24 秒 |
| 关闭所有 MCP 后重复 | chat-pro | 用量完全不变（38.7k） | ✅ 同上（**证明与 MCP 无关**） |
| 500 轮大对话"继续任务" | chat-pro | 对话消息巨大 | ❌ 静默 255 秒，`tokens=0` |

结论：卡死既不是 `chat-pro` 本身的问题（小输入 17 秒就回），也不是 system prompt、
MCP 或固定开销的问题（全新对话同样带着都正常）；唯一的变量是**对话消息体量**。
而 40k 裁剪对这个会话不够——WorkBuddy 提交的是一段约 27 万字符的 `compact-summary`，
单条消息就是一个整体，无法靠"丢最旧工具结果"拆小。

因此改用**架构性方案**：不再把整段历史塞进上下文，而是

1. 首轮把完整历史原样写成可读 Markdown 存档（`runtime/archive/<会话指纹>.md`，覆盖式更新，一条不丢）；
2. 只把最近约 `TA_RECENT_CHARS`（默认 **10000**）字符 + 一段**明确的检索指针**发给模型；
3. 指针强制要求：凡是"继续任务 / 接着做 / 之前讨论过的结论"，**动手前必须先用 grep / read 查存档**
   确认进度与待办；精确细节（字段名、路径、定过的结论）同样先查，查不到才说没有，不许编造。

实测（12 万字符历史）：首轮发给模型从 ~121k 降到 **10,266 字符（约 8%）**，
`chat-pro` 从"必卡 240 秒"变为正常推进（每轮 `in` 仅 1.2k–9.2k token），
并观测到模型确实调用 `ta_Read` / `ta_Bash` 去读文件——按需检索机制生效。

### 做出的妥协

- **默认记忆精度下降**：模型默认只看到最近约 1 万字符（约 20 条消息），更早内容不再"抬眼可见"，
  要先检索。这是用"一点细节精度"换"彻底不卡死"的主动取舍——卡死时模型表现是 0，
  换来的 80–90% 可用性远更划算。
- **多一层间接**：历史从"上下文内直达"变成"需要先读文件"，存在检索遗漏的可能。
- **依赖模型会用药**：检索能否发生，取决于客户端的模型确实具备并愿意使用文件检索工具
  （WorkBuddy 环境里是 `ta_Read` / `ta_Bash`，已验证可用）。
- **10000 是保守折中**：比初版 6000 多看约一倍近期消息以改善细节记忆，但仍明显低于
  `chat-pro` 开始吃力的输入区间；不建议盲目调高（`TA_MAX_FOLD_CHARS` 的历史数据：50k 起静默）。
- **首轮存档之外的会话增长**：首轮之后内核会话仍会随工具调用增长；0.4.3 增加了
  "预防性会话重建"（见下节）在它变大到临界点前主动换掉，但重建本身有一次存档摘要的开销。

### 可能产生的影响

- 模糊指令（如"请继续"）的续接质量更依赖检索指针是否醒目；本版指针已加 `★ 重要` 强提示。
- 精确复现早期细节（"把第 38 轮改的字段名原样贴出来"）时，模型需要先查存档才答得准，
  直接问可能含糊——此时用户可补一句"去读一下存档文件 X"。
- 存档文件含完整历史明文（含早期试错记录），位于本机 `runtime/archive/`，随 `runtime/`
  一起被 `.gitignore` 忽略，不随仓库分发；清理磁盘时可直接删，下次首轮会重建。

### 关闭方式

在 `start.cmd` 中设 `set TA_ARCHIVE_MIN_CHARS=99999999` 即回到 0.4.1 的纯裁剪行为，
或回退提交 `ab23d08`。

## 会话回收与自动续接（0.4.3）

### 为什么还需要它

0.4.2 的存档只作用于**首轮**。真实观测到一个 8 分 38 秒的长任务：全程是**同一个内核会话**，
连续几十轮工具调用，最后被 240s 看门狗掐断（`processResult` 全 0）。当时根据单一样本
推测是"`cacheRead` 涨到 7.5 万撞上临界点"。

**2026-11-17 全量日志复核后已推翻这个推测**：对 1762 条上游 cost 记录与 50 次卡死事件做关联分析，
卡死时的 `cacheRead` 从 **2.9 万到 37 万**都有，没有临界点；85 个耗时 >150s 的慢轮同样横跨
0～41 万且**绝大多数成功完成**；`in>30000` 的 110 个大输入轮**全部成功**。
结论：**卡死是上游偶发的静默断流，与上下文/cacheRead 大小没有确定阈值关系**。
（仅观察到弱相关：卡死事件的 cacheRead 中位数约 17 万，高于全体中位 10 万——更可能是
"跑得越久、轮次越多，暴露在偶发风险里的时间越长"，而非某个大小触发。）

所以 0.4.3 的两层保护中，**真正对症的是"自动续接"（失败后重建重试），而不是"预防性重建"**。

### 会话回收（膨胀兜底，非卡死预防）

`runTurn` 每轮成功后检查 `result.tokens.cache.read`：超过 `TA_RECYCLE_CACHE_CHARS`
（默认 **200000**，0.4.5 从 60000 上调）时主动放弃该会话（删会话映射，旧会话让内核自然淘汰，
不打断已完成的本轮），下一条请求走首轮存档摘要重建。

**这层只是防止会话无限膨胀的兜底，不是卡死预防**：原 6 万阈值会让约 69% 的请求在正常工作途中
被打断，且重建使 prompt 缓存归零、反而更慢。上调到 20 万后，只有真正异常庞大的会话才回收。
设 `0` 可完全关闭，交给内核自身的 compaction 管理。

### 自动续接（免手动"继续"）

`UPSTREAM_IDLE` 时，若满足**全部**以下条件，代理自动重建会话、重试一次：

- 客户端尚未中止连接（没点停止）
- **一个字都没吐给客户端**（`emitted === 0`）——保证重试不会产生重复正文
- 不是工具中继轮 / 没有 reasoning 增量（这类轮交给客户端，避免打断 MCP 调用链）

重试前清空会话映射与熔断计数 → 下一次执行走首轮存档摘要；
重试用更短的空闲看门狗 `TA_RETRY_IDLE_MS`（默认 **120000**，120 秒），
避免 240s + 240s = 480s 超过 DSH 客户端 300s 流空闲超时。
设 `TA_AUTO_RETRY=0` 可关闭。

**这就是 WorkBuddy 里"重试"按钮的代理内等价物**：DSH 或其他没有配套插件的客户端，
遇到上游静默不用手打"请继续未完成的任务"，代理会自己续接。
若重试仍失败，第二次卡死照常计入熔断（10 分钟内 2 次 → `400 CONVERSATION_STALLED`）。

### 妥协与影响

- **重建有成本**：每次重建要重新落盘存档 + 模型重新读指针/检索，且 prompt 缓存归零、后续更慢。
  因此膨胀兜底阈值设得较高（20 万），避免把正常工作中的长会话频繁打断。
- **自动续接只覆盖"零输出静默"**：如果模型已经吐了一段正文才卡住（`emitted > 0`），
  为避免重复输出不会自动重试——这种情况仍需客户端重试或手动继续。
- **重试看门狗更短（120s）**：可能把"本来 150s 会吐的长思考"误判为静默；
  但重试场景本就是异常恢复，宁可快速换干净上下文。需要时可调 `TA_RETRY_IDLE_MS`。
- **重建点在轮与轮之间**：不会打断一轮内的连续工具调用；若单轮本身就跑超长，
  只能靠下一次重建兜底。

## 连续卡死熔断

同一会话 10 分钟窗口内累计 2 次卡死（空闲超时 / 上游传输错误）后，该会话的下一次请求
直接返回 `400 CONVERSATION_STALLED` 并附处理建议，不再让客户端带着同样的
大 prompt 一轮轮重试（每次都是几分钟静默 + 超时）。成功的轮次会清除计数。

## 内核池与健康回收

- 按 `客户端类型 + 提示词指纹` 池化 kernel，LRU 上限 `TA_KERNEL_POOL_MAX`
  （默认 **3**），只淘汰闲置超过 10 分钟的实例；在途与挂起工具调用的内核不淘汰
- 每个内核带健康状态：进程退出或连续网络失败会被标记为不健康；从池中取内核时
  校验存活与健康，不健康则**剔除并重建**（清空该内核上的会话映射、起新实例）——
  下一轮从折叠首轮开始，裁剪机制保证大对话也能继续，而不是永远超时

## "输出一顿一顿"是上游网关行为

逐 chunk 计时实测（小 prompt 即复现，代理逐 delta `res.write`、无任何攒批）：

| 场景 | 思维链到达 | 正文到达 | 最长静默 |
|---|---|---|---|
| 41 字符 prompt · chat-pro | 1,111 字 = **2 个 chunk** | 489 字 = **2 个 chunk** | 11.0 秒 |
| 41 字符 prompt · chat-flash | 546 字 = **2 个 chunk** | 520 字 = **2 个 chunk** | 10.3 秒 |
| 35k 会话重放 · chat-pro | 66,500 字 = **2 个 chunk** | 964 字 = **2 个 chunk** | **163.9 秒** |

首 token（如 `"Let"`）总能在 1–3 秒单独到达 → 代理与内核都不缓冲；
静默期是**网关在上游整段缓冲**，按"阶段"（思考段 / 正文段）结束才整块刷出。
思考型模型的长回答会交替经历多个阶段，于是表现为"蹦几句话 → 卡一会 → 再蹦几句"。

代理无法也没有必要"平滑"它——数据没到就写不出来，人为拆成定时小包只会增加延迟；
心跳与看门狗的设计已适配这种节奏（大块到达即重置空闲计时）。

## 排障速查

| 现象 | 看哪里 | 处置 |
|---|---|---|
| `UPSTREAM_IDLE` 偶发 | 代理日志 + `runtime/data--kN/log/super-agent-server-*.log`（时间戳可毫秒对表） | 单次属正常，客户端重试即可；频繁出现把 `TA_MAX_FOLD_CHARS` 调小（如 30000） |
| `CONVERSATION_STALLED` | 代理日志 | 同一会话反复卡死被熔断，属保护行为；换一种问法让会话指纹变化，或重启代理 |
| 继续旧对话又超时 | 确认代理日志有"裁剪"或"长对话已存档并摘要"行 | 没有说明跑的是旧代码，重启代理 |
| 长对话用 Pro 卡 240 秒 | `runtime/archive/` 是否生成存档；代理日志"长对话已存档并摘要" | 确认走的是 0.4.2 存档模式；存档未生成检查 `TA_ARCHIVE_MIN_CHARS` 是否被调过大 |
| 模型接错上下文 / 重复做过的事 | 看它有没有调用 `ta_Read` / `ta_Bash` 读存档 | 强化问法，明确说"先读存档文件 X 确认进度"；必要时调大 `TA_RECENT_CHARS` |
| 长思考被误杀 | 代理日志的空闲超时秒数 | `TA_STREAM_IDLE_MS=280000` 提一档（**不要 ≥300000**，DSH 客户端自身 300 秒空闲超时） |
| 输出整块蹦出 | — | 上游网关行为，见上文，无需处理 |
