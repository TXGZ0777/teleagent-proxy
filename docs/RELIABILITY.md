# 稳定性与上下文管理

> 0.4.1 起的可靠性机制：为什么"重启后继续长对话必超时"、代理如何裁剪上下文、
> 看门狗与熔断的参数，以及"输出一顿一顿"的原因。

## 背景：大 prompt 的确定性超时

2026-11-17 实测（真实会话折叠重放 + 体积二分）：

| 折叠后 prompt | 结果 |
|---|---|
| 20,000 字符 | ✅ 2.5 秒完成 |
| 35,000 字符 | ✅ 秒级完成 |
| 50,000 字符 | ⚠️ 静默 75–90 秒后完成 |
| 80,000 / 150,000 / 336,000 字符 | ❌ >120 秒无内容，被看门狗/客户端掐断 |

机制：prompt 越大，模型"思考"（reasoning）产出越多，而**上游网关要等思考结束才开始吐内容**。
内核日志佐证：20k 字符输入 → 输出 777 tokens；50k → 输出 7,774 tokens。

由此形成的故障链：桌面端或代理重启后，长对话的第一轮要把整段历史折叠重放 →
巨大 prompt → 长静默 → 超时；客户端重试时每次重放同样的内容 → **确定性失败**，
只能反复手动发"请继续"。0.4.1 起在四个层面处理这个问题。

## 四层上下文控制

| 层 | 环境变量 | 默认 | 行为 |
|---|---|---|---|
| 单轮总体积 | `TA_MAX_FOLD_CHARS` | `40000` | 首轮折叠与增量轮共用同一预算：超限时**优先丢弃最旧的工具结果**（用户/助手主线保真），文本头注明省略；工具结果丢完仍超限才截尾保留最近内容。`0`=关闭 |
| 单条工具结果 | `TA_MAX_TOOL_CHARS` | `12000` | 超长工具结果保留 60% 头 + 40% 尾，中间标"省略 N 字符"。`0`=关闭 |
| 流空闲看门狗 | `TA_STREAM_IDLE_MS` | `240000` | 该时间内**内容没有任何增长**才判定上游静默断流（错误码 `UPSTREAM_IDLE`）。思维链增长、正文增长、新的 assistant 消息都算活跃；重复回吐同一段文本骗不过它。`0`=关闭 |
| 单轮总时长 | `TA_TURN_TIMEOUT_MS` | `1200000` | 一轮 20 分钟硬上限 |

设计原则：

- **丢最旧的工具结果，不丢对话主线**——用户意图与模型已得出的结论完整保留；
  被裁掉的早期工具输出在需要时模型会重新调用工具获取，代价是多一轮往返
- 模型始终被告知有省略（折叠文本头部标记），不会把裁剪后的内容当成完整历史
- 三协议（`/v1/chat/completions`、`/v1/responses`、`/v1/messages`）的折叠与裁剪行为一致

裁剪发生时代理日志会出现（时间戳格式，可与内核日志毫秒级对表）：

```
[2026/11/17 08:23:40.123] 首轮折叠文本裁剪：省略 8 条工具结果，剩余 20073 字符
[2026/11/17 08:23:40.456] 增量轮裁剪：省略 2 条、截取 1 条工具结果，本轮 39812 字符
```

## 看门狗为什么是 240 秒

实测"活着但静默思考"的窗口随 prompt 变大：50k 字符静默 75–90 秒属正常；
真实会话 35k 重放中观测到 **163.9 秒完全静默后一次性返回 66,500 字思维链**。
120 秒（0.4.0 默认）会把这类本来能完成的轮次误杀；240 秒给足长思考耐心，
又略短于 DSH 客户端自身的 300 秒流空闲超时——真卡死时，可定位的
`UPSTREAM_IDLE` 错误会先从代理报出，而不是客户端笼统超时。

## 连续卡死熔断

同一会话 10 分钟窗口内累计 2 次卡死（空闲超时 / 上游传输错误）后，该会话的下一次请求
直接返回 `400 CONVERSATION_STALLED` 并附处理建议，不再让客户端带着同样的
大 prompt 一轮轮重试（每次都是几分钟静默 + 超时）。成功的轮次会清除计数。

## 内核池与健康回收

- 按 `客户端类型 + 提示词指纹` 池化 kernel，LRU 上限 `TA_KERNEL_POOL_MAX`
  （默认 **3**），只淘汰闲置超过 10 分钟的实例；在途与挂起工具调用的内核不淘汰
- 每个内核带健康状态：进程退出或连续网络失败会被标记为不健康；从池中取内核时
  校验存活与健康，不健康则**剔除并重建**（清空该内核上的会话映射、起新实例）——
  下一轮从折叠首轮开始，裁剪机制保证大对话也能继续，而不是永远超时

## "输出一顿一顿"是上游网关行为

逐 chunk 计时实测（小 prompt 即复现，代理逐 delta `res.write`、无任何攒批）：

| 场景 | 思维链到达 | 正文到达 | 最长静默 |
|---|---|---|---|
| 41 字符 prompt · chat-pro | 1,111 字 = **2 个 chunk** | 489 字 = **2 个 chunk** | 11.0 秒 |
| 41 字符 prompt · chat-flash | 546 字 = **2 个 chunk** | 520 字 = **2 个 chunk** | 10.3 秒 |
| 35k 会话重放 · chat-pro | 66,500 字 = **2 个 chunk** | 964 字 = **2 个 chunk** | **163.9 秒** |

首 token（如 `"Let"`）总能在 1–3 秒单独到达 → 代理与内核都不缓冲；
静默期是**网关在上游整段缓冲**，按"阶段"（思考段 / 正文段）结束才整块刷出。
思考型模型的长回答会交替经历多个阶段，于是表现为"蹦几句话 → 卡一会 → 再蹦几句"。

代理无法也没有必要"平滑"它——数据没到就写不出来，人为拆成定时小包只会增加延迟；
心跳与看门狗的设计已适配这种节奏（大块到达即重置空闲计时）。

## 排障速查

| 现象 | 看哪里 | 处置 |
|---|---|---|
| `UPSTREAM_IDLE` 偶发 | 代理日志 + `runtime/data--kN/log/super-agent-server-*.log`（时间戳可毫秒对表） | 单次属正常，客户端重试即可；频繁出现把 `TA_MAX_FOLD_CHARS` 调小（如 30000） |
| `CONVERSATION_STALLED` | 代理日志 | 同一会话反复卡死被熔断，属保护行为；换一种问法让会话指纹变化，或重启代理 |
| 继续旧对话又超时 | 确认代理日志有"裁剪"行 | 没有说明跑的是旧代码，重启代理 |
| 长思考被误杀 | 代理日志的空闲超时秒数 | `TA_STREAM_IDLE_MS=280` 提一档（**不要 ≥300**，DSH 客户端自身 300 秒空闲超时） |
| 输出整块蹦出 | — | 上游网关行为，见上文，无需处理 |
